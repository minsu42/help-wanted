## 왜 이 문서가 있는가

배정 화면이 게임을 멈춘다. 가용한 모험가가 전부 배정을 거부하면 체크할 사람이 없어
`confirm`이 영구히 비활성인데, 그 단계에는 나가는 버튼이 없다.

**측정 (2026-08-09, 자동 플레이 6회 시행)**: P0 이전 빌드(b631f1a) 6/6 막힘,
P0 이후 3/6. 시드가 `Date.now()`(`main.ts:151`)라 확률적으로 발생한다.
P0가 만든 버그가 아니라 그 전부터 있었다.

`production/roadmap.md`의 **「`main`은 항상 배포 가능한 상태여야 한다」**와 정면으로
부딪히며 제출 마감이 임박했다.

## 1. 근본 원인 — 밸런스가 아니라 산술이다

조사 결과 전원 거부는 드문 사고가 아니라 **신뢰 수치의 필연적 귀결**이었다.

| 값 | 출처 | 크기 |
| ---- | ---- | ---- |
| `world.guildInitialTrust` | 길드원 시작 신뢰 | 0.5 |
| `rumor.trustOnDeath` | 사망 시, **생존 길드원 전체** | −0.15 |
| `rumor.trustOnDeceit` | 은폐했으면 추가로 | −0.35 |
| `dispatch.assignmentTrustThreshold` | 이 아래면 거부 | 0.15 |
| `rumor.trustOnSurvive` | 회복 수단 (파견을 나가야 받는다) | +0.05 |

사망 페널티가 **길드원 전체에게 균일하게** 적용된다는 점이 결정적이다
(`reputation.ts`의 `bystanders` 경로). 그래서 신뢰는 개인별로 흩어지지 않고
**한 덩어리로 함께 내려간다.**

- **은폐 사망 1회**: 0.5 − 0.50 = **정확히 0.0.** 길드원 전원이 동시에.
- **정직한 사망 3회**: 0.5 − 0.45 = 0.05 < 0.15. 역시 전원.

회복은 `trustOnSurvive` +0.05뿐인데 그것은 **파견을 나가야** 받는다. 아무도 안 나가므로
회복 경로가 닫힌다.

### 따라서 임계값 조정으로는 고쳐지지 않는다

`assignmentTrustThreshold`가 0.15든 0.01이든 **0보다 크기만 하면 똑같이 잠긴다.**
임계값이 높은 것이 문제가 아니라 **페널티 합이 시작 신뢰와 같은 것**이 문제다.
이 스펙이 임계값을 손대지 않는 이유가 그것이다.

### 남아 있던 유일한 밸브 — 영입

외부 모험가는 `inGuild` 필터에서 빠져 사망 페널티를 맞지 않고(`gameState.ts`의
`bystanders`), 영입 시 `trust`가 `recruit.initialTrust`(0.25)로 세팅된다
(`guild.ts`). 사망으로 정원 한 칸이 비므로(`activeGuildRosterSize`가 사망자를 세지
않는다) 실제로 뚫린다.

**단 확실하지 않다** — 방문자가 홀에 와야 하고(`visitorMin: 0`) 135~330G가 있어야
한다. 그래서 탈출구만 달면 "멈춘 게임"이 "걸어다니는 시체"가 된다.

## 2. 결정

| # | 질문 | 결정 |
| ---- | ---- | ---- |
| 1 | 나가면 그 의뢰는 어떻게 되는가 | **열린 채로 창구에 남는다** |
| 2 | 타결된 계약과 `offersMade`는 | **조건 유지, 재협상 없음.** `offersMade`는 되돌리지 않는다 |
| 3 | 전원 거부가 정상 상태인가 | **아니다. 배정 거부를 게이트에서 대가로 바꾼다** |
| 4 | 신뢰 고갈이 패배 조건인가 | **지금은 아니다. P4에서 결정** |

### 왜 「열린 채로」가 기본값인가

`dispatchParty`가 `openContracts`에서 계약을 빼는 것은 **확정 시점**이다
(`gameState.ts`). 배정 화면에 서 있는 동안 의뢰는 아직 열려 있으므로,
「열린 채로 돌아간다」는 도메인 변경이 **0줄**이다. 오히려 「파기한다」가 코드를
추가해야 하는 쪽이었다.

### 왜 재협상을 막는가

`evaluateOffer`는 `offerNumber >= maxOffers`면 무조건 결렬이다(`negotiation.ts`).
`maxOffers`가 3이므로 타결은 1~2회차에서만 일어나고, `offersMade`는 이미 그 횟수를
세어 두었다. 창구로 돌아가 **아무 선택지나 한 번 더 누르면 그것이 3회차라서 조건과
무관하게 결렬**되고 카드가 걷힌다 — 「열린 채로 유지」가 실질적으로 파기가 된다.

`offersMade`를 리셋하는 대안은 채택하지 않았다. `gameState.ts`가 그 필드를 화면이
아니라 세션 상태에 둔 이유가 **재진입으로 결렬 규칙을 우회하는 것을 막기 위해서**이며,
이 스펙이 그것을 정면으로 뒤집을 이유가 없다.

## 3. 배정 꺼림 — 규칙

**거부(refusal)를 꺼림(reluctance)으로 바꾼다.** 판정 조건은 그대로 두고 **강제력만**
없앤다.

| 조건 | 이전 | 이후 |
| ---- | ---- | ---- |
| `trust < assignmentTrustThreshold` | 체크박스 비활성 | 경고 표시. 체크 가능 |
| `goal === 'survival'` && `statedRisk > survivalRefusalRisk` | 체크박스 비활성 | 경고 표시. 체크 가능 |

**두 조건이 함께 풀린다.** 하나만 남기면 그 하나로 똑같이 얼어붙는다 — 특히
`survivalRefusalRisk`(90)는 명성이 오르면 도달하므로 후반에 같은 정지가 재현된다.

### 강행의 대가

확정 시 꺼리는 상태였던 인원 각각에게:

- `trust` += `dispatch.forcedAssignmentTrustPenalty` (**−0.1**)
- `Memory { kind: 'forcedAssignment' }` 추가

**−0.1의 근거**: `trustOnWound`(−0.1)와 같은 크기. *"내키지 않는데 보내졌다"* 가
*"다쳐서 돌아왔다"* 와 같은 무게라는 뜻이다. `trustOnDeath`(−0.15)보다는 가볍다 —
사람이 죽은 것보다 무거울 수는 없다. P8 밸런스 패스의 조정 대상이다.

### 사유 문구는 지우지 않는다

체크박스에서 `disabled`만 빼고 사유 텍스트는 **남긴다.** 문장만 경고형으로 바꾼다.

| 이전 | 이후 |
| ---- | ---- |
| 아직 이 길드를 믿지 않아 배정을 받아들이지 않는다. | 아직 이 길드를 믿지 않는다. 강행하면 신뢰를 더 잃는다. |
| {생존}을 최우선으로 여겨 이만큼 위험한 배정은 사양한다. | {생존}을 최우선으로 여긴다. 강행하면 신뢰를 더 잃는다. |

정보를 없애는 것이 아니라 **강제력만** 없애는 것이 요점이다. 회색 체크박스가 아무
설명 없이 사라지면 플레이어는 그런 규칙이 있다는 것조차 모른다 — `CounterScreen`의
「비활성 사유를 반드시 적는다」와 같은 규약이다.

### 「진짜 드물게 거부」를 채택하지 않은 이유

드문 하드 게이트는 같은 버그를 **더 찾기 어려운 형태로** 남긴다. 이 버그가 지금까지
살아남은 이유가 정확히 시드가 `Date.now()`라 확률적이었다는 것이다 — 개발 중에는
안 보이고 6회 중 3회에서만 터졌다. 되살릴 이유가 없다.

## 4. 탈출구

**배정 거부를 풀어도 여전히 필요하다.** 남은 경로가 있다 — 가용 길드원이 **0명**일 때
(예: 사망 3 + 부상 2 + 파견 중 3). 그러면 행이 아예 없어서 강행할 대상조차 없다.

- `assigning` 단계에 「나중에 배정한다」(`data-action="return"`)
- `waiting` 단계에도 같은 버튼. 이미 파견이 나갔으므로 나가도 안전하고
  (`endDay`가 결과를 큐에 넣는다), 그러면 **탈출구 없는 단계가 이 화면에서 0개**가 된다

## 5. 타결 조건 보존

`Settlement`는 프레젠테이션 타입이라 `GameState`가 참조할 수 없다. 도메인에 최소
형태를 새로 둔다.

```ts
// domain/types.ts
export interface SettledTerms {
  readonly agreedReward: number;
  readonly discloseRisk: boolean;
}

// GameState
settlements: Record<string, SettledTerms>;
```

- **쓰기**: 창구에서 타결되는 순간
- **삭제**: `dispatchParty`가 그 계약을 소비할 때 (열린 의뢰에서 사라지는 것과 같은 시점)
- **읽기**: 창구가 그 의뢰를 그릴 때. 타결된 의뢰는 흥정 선택지 대신
  **「이미 타결된 조건 — N G / 위험 고지 여부」 + 「배정하러 간다」**를 보여준다

`offersMade`는 손대지 않는다.

## 6. Tuning Knobs

| 노브 | 값 | 범위 | 성격 | 방향 |
| ---- | ---- | ---- | ---- | ---- |
| `dispatch.forcedAssignmentTrustPenalty` | −0.1 | −0.3 ~ 0 | cost | 크게 — 강행이 공짜면 꺼림이 장식이 된다. 단 `trustOnDeath`(−0.15)를 넘지 말 것 |
| `dispatch.assignmentTrustThreshold` | 0.15 | 0.0~0.4 | **warning** | **성격이 바뀌었다** — 게이트가 아니라 경고 표시 임계값이다. 이제 올려도 게임이 멈추지 않는다 |
| `dispatch.survivalRefusalRisk` | 90 | 60~200 | **warning** | 위와 같다. 이름의 `Refusal`이 더 이상 정확하지 않으나 개명은 하지 않았다 — 이 변경의 범위를 넘는다 |

## 7. 알려진 한계 — P4로 넘기는 것

### 강행의 대가는 신뢰가 0일 때 무력하다

은폐 사망으로 전원 0.0이 된 바로 그 상태에서는 −0.1을 깎을 것이 없다
(`applyTrust`가 0에서 클램프한다). 즉 **가장 강행하고 싶은 순간에 강행이 공짜다.**

이것은 P4의 **「길드 탈퇴」**가 답이다 — 신뢰가 아니라 **사람이 떠나는 것**이 바닥에서도
작동하는 유일한 대가다. 이번 변경에서는 고치지 않는다.

### 착취 억제 회로가 약해졌다

`reputation.ts` 상단이 배정 거부를 *"착취가 정보망을 스스로 조이게 만드는 유일한
기계적 장치"*라고 적어 두었다. 게이트를 풀면 신뢰가 낮아도 계속 굴릴 수 있으므로
압력이 준다.

남는 압력은 소문 임계값(`trustThresholdDefault: 0.4` 등 — 신뢰가 낮으면 정보를
말해주지 않는다)뿐이다. **정보가 마르는 것이 사람이 안 나가는 것을 대체할 만큼
아픈가**는 P8 밸런스 패스에서 확인할 항목이다.

### `forcedAssignment` 기억은 지금 쓰기 전용이다

읽는 곳이 아직 없다. `sentToDanger`·`sentSafe`·`wasDeceived`도 같은 상태이며
(`OutcomeScreen`이 `lostComrade`만 읽는다), P4의 「길드원 조언」과 「상실 반응」이
이들을 함께 소비한다.

### 하루를 구간으로 나누는 안

「의뢰인 구간 → 길드 홀 구간 → 재정 관리 구간」으로 하루를 나누는 구조가 검토됐고
**방향은 채택하되 시점은 P3으로 미뤘다.**

- 페이즈를 나눠도 이 버그는 안 고쳐진다 — 막다른 길은 화면 *사이*가 아니라 배정 화면
  *안*에 있었다
- 로드맵 P3에 이미 절반이 있다 (「하루 마감 화면」 = 재정 관리 구간,
  「하루 행동 횟수」 = 구간을 나누는 예산)
- P1이 창구를 다시 짓는다. 그 전에 구간 경계를 그으면 두 번 짓게 된다
- `roadmap.md`가 *"마감 며칠 전에 큰 리팩터링을 시작하지 않는다"* 를 요구한다

기록 위치: `production/roadmap.md` P3.
