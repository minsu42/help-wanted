# Quick Design Spec: 계약 협상 (흥정 시스템)

**Type**: New Small System
**System**: 계약 협상 (systems-index #9, Feature 레이어, Tier 0)
**GDD Reference**: 없음 — 이 프로젝트는 `/design-system` 정식 GDD를 스킵한다
(`design/gdd/game-concept.md` Next Steps 참조). 상위 컨셉은
`design/gdd/game-concept.md`의 Core Mechanics / MVP Definition 절.
**Date**: 2026-08-08
**Scope**: 의뢰인이 제시한 의뢰를 3개 축으로 흥정해 타결/결렬시킨다.
모험가 배정과 파견 판정은 포함하지 않는다.
**Estimated Implementation**: 4~5시간

---

## Overview

의뢰인이 창구에 앉으면 플레이어는 **보상 / 선불 / 위험 고지** 세 축으로 계약 조건을
제안한다. 의뢰인은 자신의 숨은 상태(`wealth`, `urgency`, `hasAlternative`)에 따라
감내 가능한 총 부담량이 정해져 있고, 제안의 부담이 그 한도 안이면 수락한다.

판정은 **완전히 결정론적**이다. 난수가 개입하면 정보가 흥정력이 되지 못한다 —
아는 만큼 정확히 예측할 수 있어야 이 게임의 핵심 원리("정보 = 흥정력")가 성립한다.

### 왜 세 축인가 (기한 축을 뺀 근거)

축 하나가 값을 하려면 **(a) 다른 축과 구별되는 결정**, **(b) 숨은 정보가 답을 바꿈**,
**(c) 대가가 있음** 세 가지가 필요하다. (b)가 빠지면 그 축은 이 게임의 축이 아니라
그냥 슬라이더다.

| 축 | 어떤 숨은 정보가 답을 바꾸나 | 판정 |
|---|---|---|
| 보상 | `wealth`, `urgency`, `hasAlternative` 셋 다 | 기준축 |
| 선불 | `wealth` — 떼일 것인가 | 정보 축 |
| 위험 고지 | 실제 위험도 — **정보가 없으면 축 자체가 안 열린다** | 정보 축 |
| ~~기한~~ | **없음** | 제거됨 |

기한 축에서는 *"아, 내가 알고 있었지"* 하는 순간이 발생하지 않는다. `urgency`가 얼마나
양보하는지를 정하긴 하지만 그것은 모든 축에 걸리는 공통 계수이지 기한만의 함정이
아니다. 게다가 기한을 협상 대상으로 두면 파견 판정(기한 페널티)과 모험가 명부(구속
일수) **두 시스템에 추가 결합**이 생긴다 — 정보 게임에 기여하지 않으면서 결합만
늘리는 축이다.

**기한을 없앤 것이 아니라 협상 대상에서 뺐다.** 소요 일수는 의뢰의 고정 속성
(`durationDays`)이고 모험가는 그만큼 묶인다. 일정 압박(경영 시뮬의 뼈대)은 그대로
남고, 슬라이더 하나와 결합 두 개가 사라진다.

남은 세 축은 **전부 정보 축**이다 — 축 구성 자체가 기둥 1("아는 자가 이긴다")을
말한다.

> **컨셉 문서와의 차이**: `game-concept.md`의 Open Question 1은 "많으면 선불을 잘라
> 3개 축으로"라고 적었다. 이 스펙은 반대 결론을 내렸다 — 선불은 `wealth` 하나를 두
> 갈래 행동으로 가르는 정보 축이고, 잘라야 할 것은 비밀이 없는 기한 축이다.
> Open Question 1은 이로써 종결한다.

## Core Rules

### 1. 세 개의 축

| 축 | 플레이어가 하는 일 | 의뢰인에게 주는 부담 | 플레이어가 치르는 대가 |
|---|---|---|---|
| **보상** | 기준 보상 대비 배율을 요구 | 요구 배율에 비례 | 없음 (순수 요구) |
| **선불** | 보상의 몇 %를 선지급받을지 | 선불 비율에 비례 | 없음 — 대신 **떼일 위험을 막는다** |
| **위험 고지** | 실제 위험을 계약서에 명시 | 부담이 아님 — **허용치를 올린다** | `hasAlternative` 의뢰인은 떠날 수 있다 |

### 2. 위험 고지는 정보가 있어야만 열리는 축이다

플레이어가 해당 의뢰의 **실제 위험도를 소문으로 알아낸 상태**
(`PlayerKnowledge.revealedFacts`에 해당 사실 id가 있음)이고 **실제 위험도 > 공개
위험도**일 때만 이 축을 켤 수 있다. 모르면 UI에서 비활성이다.

이것이 "정보 = 흥정력"의 가장 직접적인 구현이다. 다른 두 축은 정보 없이도 조작할 수
있지만(불리할 뿐), 이 축은 **정보 없이는 존재하지 않는다.**

### 3. 수용 판정

```
burden    = w_reward  × max(0, 보상배율 − 1)
          + w_advance × 선불비율

tolerance = toleranceBase
          + wealthWeight  × wealth        // 부유하면 더 준다
          + urgencyWeight × urgency       // 급하면 더 준다
          − alternativePenalty            // hasAlternative일 때만
          + disclosureBonus               // 위험 고지를 켰을 때만

수락 = burden ≤ tolerance
```

`wealth`, `urgency`는 0~1 정규화 값이다 (`src/domain/types.ts`의 `Client`).
`선불비율`도 0~1이다. `보상배율`은 1.0이 기준 보상.

### 4. 제안 횟수와 결렬

1. 플레이어가 제안한다. `burden ≤ tolerance`면 **타결**.
2. 거부되면 의뢰인은 **기여도가 가장 큰 축 하나를 지목**해 반박한다
   ("선불은 도저히 안 되겠소"). 이 반박 자체가 숨은 상태에 대한 정보다.
3. 두 번째 제안이 거부되면 **결렬**. 그 의뢰는 사라지고, 숨겨져 있던 진실은 영원히
   밝혀지지 않는다.

`hasAlternative`이고 위험 고지를 켠 경우, 1회차 거부 시 반박 없이 **즉시 결렬**한다 —
다른 길드로 갔다.

### 5. 계약 이후 (다른 시스템으로의 출력)

- **잔금 미지급**: 의뢰 완료 시 잔금 지급 여부는 `wealth`로 판정한다. `wealth`가 낮으면
  떼인다. **선불로 받은 몫은 무조건 확정이다** — 이것이 선불 축의 존재 이유다.
- **미지급의 학습 효과 보완**: 선불 축은 페이오프가 며칠 뒤에 오고 15일 회차에서
  떼이는 경험이 2~3번뿐이라 학습이 느리다. 완화책으로, 미지급이 발생하면 결과 대조
  화면에서 크게(붉은 봉랍색) 표시하고 **해당 의뢰인의 `wealth`를 영구 공개**한다.
  한 번 떼이면 그 사람에게는 두 번 다시 속지 않는다.
- **침묵의 대가**: 실제 위험을 **알고도** 고지하지 않은 계약에서 사망이 발생하면,
  길드원들의 `trust`가 하락하고 `Memory.kind = 'wasDeceived'`가 기록된다. 신뢰가
  낮으면 소문을 말해주지 않는다 — 착취가 정보망을 스스로 조인다.
- **구속 일수**: 의뢰의 `durationDays` 동안 배정된 모험가는 `onMission` 상태가 된다.
  협상 대상이 아니라 의뢰의 고정 속성이다.

## Tuning Knobs

| Knob | Default | Range | Category | Rationale |
|---|---|---|---|---|
| `w_reward` | 1.0 | 0.5–2.0 | curve | 기준축. 나머지 가중치는 이것 대비로 읽는다 |
| `w_advance` | 0.8 | 0.3–1.5 | curve | 현금 흐름은 총액보다 아프다 |
| `toleranceBase` | 0.35 | 0.1–0.8 | gate | 정보 없이도 약간은 흥정되게 하는 하한 |
| `wealthWeight` | 0.5 | 0.2–1.0 | curve | 자금력이 보상 상한을 지배하지 않도록 억제 |
| `urgencyWeight` | 0.6 | 0.2–1.2 | curve | 급박함이 가장 큰 지렛대여야 흥정이 재밌다 |
| `alternativePenalty` | 0.25 | 0.1–0.6 | gate | 대안이 있으면 확실히 불리하되 협상 불가는 아니게 |
| `disclosureBonus` | 0.4 | 0.1–0.8 | gate | 정보 1개의 현금 가치. **밸런싱 1순위 노브** |
| `maxOffers` | 2 | 1–3 | feel | 1이면 가혹, 3이면 시행착오로 정보 없이 풀린다 |

전부 `src/data/balance.json`의 `negotiation` 섹션에 들어간다. 코드에 상수를 박지 않는다.

> **경로 주의**: 이 프로젝트는 템플릿 기본값인 `assets/data/`를 쓰지 않는다.
> `tsconfig.json`의 `include`가 `["src", "tests"]`이므로 `src/` 밖의 JSON은
> 타입체크 대상에서 빠진다.

## Acceptance Criteria

- [ ] 같은 의뢰인 + 같은 제안이면 **항상 같은 결과**가 나온다 (난수 미개입)
- [ ] `urgency`가 높은 의뢰인은 낮은 의뢰인보다 더 큰 `burden`을 수락한다
- [ ] `hasAlternative` 의뢰인은 동일 조건에서 더 적은 `burden`만 수락한다
- [ ] 실제 위험도를 모르는 상태에서는 위험 고지 축이 **비활성**이다
- [ ] 실제 위험도 ≤ 공개 위험도이면 알고 있어도 위험 고지 축이 비활성이다
- [ ] 위험 고지를 켜면 동일 제안의 수용 범위가 `disclosureBonus`만큼 넓어진다
- [ ] 1회차 거부 시 **기여도 최대 축**이 지목된다 (다른 축이 지목되지 않는다)
- [ ] `hasAlternative` + 위험 고지 + 1회차 거부 → 반박 없이 즉시 결렬
- [ ] 미지급 발생 시 해당 의뢰인의 `wealth`가 `PlayerKnowledge`에 영구 기록된다
- [ ] 모든 노브가 `balance.json`에서 읽힌다 — 코드에 리터럴 숫자 없음
- [ ] 회귀: 결렬된 의뢰의 실제 정보는 어떤 화면에도 노출되지 않는다

**필수 테스트**: `.claude/docs/technical-preferences.md`의 3대 필수 테스트 중 1번
("흥정 수용 판정 — 의뢰인의 숨은 상태별 조건 수용 범위")이 이 시스템이다.
위 항목 2·3·6을 단위 테스트로 고정한다.

## Tier 1 후보: 단골 계약

**기록해두는 이유**: 현재 설계에는 구조적 편향이 하나 있다 — **관대할 이유가 전혀
없다.** 세 축이 모두 더 뜯어내는 쪽을 가리키고, MDA의 Expression 축("정직한 중개인이
될지 착취자가 될지")을 지탱하는 것은 위험 고지 침묵으로 인한 `trust` 하락 하나뿐이다.

**아이디어**: 관대하게 타결한 의뢰인이 나중에 더 좋은 조건으로 돌아온다. 정직에
처음으로 기계적 보상이 붙는다.

**MVP에 넣지 않는 이유**: 15일 안에 재방문이 성립하려면 의뢰인 재등장 로직이 필요하고,
플레이어에게 "미래 가치 계산"이라는 새 인지 부하를 얹는다. 3일 안에 넣으면 반쯤
작동하다 말 확률이 높다.
