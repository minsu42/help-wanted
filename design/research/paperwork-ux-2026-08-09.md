# 의뢰서 작성 UX — 사례 조사 및 설계 권고

**Date**: 2026-08-09
**질문**: 의뢰서 작성이 플레이어에게 반복 노동이 되지 않는가?
**결론**: 위험은 실재한다. 해법은 칸을 줄이는 것이 아니라 **받아쓰기와 판단을
분리하고, 꼼꼼함에 비용을 붙이는 것**이다.

**적용 범위**: 창구의 청취·의뢰서 작성 단계. 협상(`contract-negotiation-*.md`)과
파견 판정(`dispatch-resolution-*.md`)은 이 문서의 범위가 아니다.

---

## 1. 문제 정의

의뢰서에 칸이 여러 개 있고 회차당 의뢰가 수십 건이면 **같은 서식을 수십 번
채운다.** Sid Meier의 기준을 그대로 대면 이렇게 된다:

> 흥미롭지 않은 결정 = **플레이어가 항상 첫 번째를 고르게 되는 것**

칸 하나라도 "정보를 옮겨 적기만 하면 되는" 칸이면 그 칸은 결정이 아니라 노동이다.
그리고 노동은 수십 번 반복되면서 게임 전체의 인상을 결정한다.

---

## 2. 사례 조사

### 2.1 The Case of the Golden Idol — 타입 제약이 탐색을 좁힌다

수집한 단어를 빈칸에 드래그해 문장을 완성한다. **타이핑이 없다.**

- 단어에 색이 있다: 이름=갈색, 장소=회색, 물건=황갈색, 동사=파랑
- **빈칸에도 같은 색이 칠해져 있어 색이 안 맞으면 넣을 수 없다**
- 구간 단위로 검증한다. 전부 맞으면 잠기고, 틀린 개수만 알려준다

→ **타입 제약이 작성을 노동에서 추론으로 바꾼다.** 넣을 수 있는 후보가 셋뿐이면
"채우는 것"이 아니라 "고르는 것"이 된다.

### 2.2 Return of the Obra Dinn — 부분 정답은 주되, 어디가 틀렸는지는 감춘다

60명의 이름·사인·가해자를 장부에 채운다.

- **3개가 전부 맞아야 확정된다.** 개별 검증하면 조합을 브루트포스할 수 있어서다
- 5개를 적었는데 3개만 확정되면 나머지 둘이 틀렸다는 건 알지만 **어느 것인지는
  모른다**
- 54명을 넘기면 기준이 2개로 완화된다 (막판 가속)

→ **피드백의 해상도를 낮추는 것이 퍼즐을 만든다.** 다만 이 게임에는 그대로
쓰지 않는다 — §5 참조.

### 2.3 Papers, Please — 물리적 조작감 + 처리량 압박

Lucas Pope의 출발점은 주제가 아니라 촉감이었다:

> *"종이를 이리저리 옮기는 것 자체가 나에게 재미있었다. 그래서 그걸 기반으로
> 쌓았다."*

압박 구조는 이렇다:

- 하루가 시계로 흐른다 (6시 → 18시)
- **줄은 사실상 무한하다.** 다음 사람을 부르면 계속 온다
- 처리한 인원 수가 곧 수입이고, 그 수입으로 가족을 부양한다
- 서두르면 실수하고, 실수하면 경고장과 벌금이 온다

> **주의 — 흔한 오해**: Papers, Please에는 **대기하다 떠나는 손님이 없다.**
> 초조해하는 대기열은 식당 경영 게임(손님 인내심 미터)의 문법이며 이 게임의
> 참고 대상이 아니다. Papers, Please의 압박은 오직 **시계와 처리량**이다.

→ **처리량 압박이 "꼼꼼함"을 미덕에서 선택으로 바꾼다.** 이것이 서류 작업이
노동이 되지 않는 가장 강한 장치다.

### 2.4 입력 방식 — Her Story / Do Not Feed the Monkeys / Duskers

| 게임 | 방식 | 자동완성 |
|---|---|---|
| Her Story | 검색창 자유 타이핑, 상위 5개만 반환 | 없음 (의도적 불친절) |
| Do Not Feed the Monkeys | 수집한 단어를 **클릭하면 검색창에 입력** | 클릭 입력 |
| Duskers | 커맨드라인 | 있음 (TAB/SPACE/ENTER로 완성) |
| 파서 IF (Zork 계열) | 완전 자유 문장 | 없음 → *guess the verb*가 40년째 미해결 |

→ 성공한 사례의 공통점은 자동완성 유무가 아니라 **검색어의 출처가 게임 안에
있다**는 것이다. Her Story조차 시작할 때 `murder`가 미리 입력되어 있다.
**무에서 발상하게 하는 게임은 없다.**

파서 IF 쪽에서 알려진 해법 셋:

1. 받아들이는 동사·명사를 미리 다 알려준다
2. Storytron(Chris Crawford)은 문장 성분별 드롭다운을 주고 **유효한 조합만** 제시
3. 동의어를 최대한 많이 코딩한다

그리고 통계 하나: **가장 흔한 동사 100개가 전체 행동의 95%를 차지한다.** 무한한
자연어를 다 받을 필요가 없다는 뜻이며, §4.3의 키워드 사전 방식의 근거가 된다.

### 2.5 Sid Meier — 흥미로운 결정의 정의

- 흥미로운 결정: 어느 선택도 명백히 낫지 않고, 선택지들이 동등하게 매력적이지도
  않으며, 플레이어가 **정보에 근거해** 고를 수 있다
- 흥미롭지 않은 결정: 항상 첫 번째를 고르는 것, 무작위로 고르는 것
- **지루한 부분은 자동화하거나 제거한다**
- 복잡한 결정이 연달아 오면 통제감을 잃고, 단순한 결정이 느리게 오면 지루하다

## 4. 이 게임에 적용한 설계

### 4.1 의뢰서의 구조 — 두 종류의 칸

의뢰서는 **받아쓰기 칸**과 **판단 칸**으로 나뉜다. 이 분리가 이 설계의 전부다.

```
┌─ 의뢰서 ─────────────────────────────────────────┐
│                                                   │
│  [받아쓰기 칸] — 청취로 알아내면 자동으로 채워진다  │
│    의뢰인 : 마르타 (로웰 마을 주민)                 │
│    종류   : 조사                                   │
│    대상   : 대형 미상                              │
│    규모   : ?           ← 묻지 않았다              │
│    장소   : 북쪽 숲                                │
│                                                   │
│  ─────────────────────────────────────────────    │
│                                                   │
│  [판단 칸] — 플레이어가 직접 정한다                 │
│    추정 위험도 : [ D ][ C ][ B ][ A ][ S ]         │
│    권장 인원   : [ - ][ 1 ][ 2 ][ 3 ][ + ]         │
│    특이사항    : + 야간 활동 가능성                 │
│                  + 민간인 존재 가능성               │
└───────────────────────────────────────────────────┘
```

**받아쓰기 칸은 플레이어가 손대지 않는다.** 청취에서 알아낸 것이 그대로 옮겨진다.
정보를 옮겨 적는 것은 결정이 아니므로 자동화한다 (원칙 1).

**판단 칸이 유일하게 흥미로운 결정이다.** 그리고 이 칸이 이 게임의 정체성이다 —
**플레이어가 적은 위험도가 실제로 모험가에게 전달되는 정보**이기 때문이다.
C급이라고 적으면 모험가는 C급 준비를 하고 간다. 실제가 B급이었다면 그 격차만큼
사람이 죽는다.

> 사람이 죽었을 때 플레이어의 머릿속에 남는 문장이 달라진다.
> *"정보가 부족했다"* (수동) → **"내가 C급이라고 적었다"** (책임)

### 4.2 특이사항 — 토큰을 붙인다

특이사항 칸에는 **청취·소문으로 수집한 단서 토큰만** 넣을 수 있다 (원칙 2).
자유 입력이 아니다.

```
  수집한 단서:  [야간에 나타남]  [발자국이 큼]  [아이들이 논다]  [가축만 노림]
                 ↑ 청취           ↑ 청취          ↑ 소문          ↑ 청취
```

토큰에는 타입이 있고(시간 / 흔적 / 위험 / 지형), 특이사항 슬롯도 같은 타입만
받는다. Golden Idol의 색 제약과 같다 — **틀린 조합이 애초에 불가능하므로 작성이
빨라지고, 남는 것은 "무엇을 적고 무엇을 뺄 것인가"라는 결정뿐이다.**

토큰을 다 붙이면 좋은 것이 아니다. **모험가는 의뢰서를 읽는 데도 시간을 쓴다** —
특이사항이 많으면 준비가 늘어지고 출발이 늦어진다. 정말 중요한 것만 골라야 한다.

### 4.3 청취 입력 — 클릭 + 자유 타이핑 + 자동완성

세 방식을 겹쳐 쓴다. 각각이 다른 실패 모드를 막는다.

#### ① 클릭 입력 — 무에서 발상하지 않게 한다

의뢰인의 대사에서 단어를 클릭하면 입력창에 들어간다.

```
  마르타: "발자국을 봤습니다. 커다란 발자국이요."
                ────           ────
```

Do Not Feed the Monkeys 방식 (원칙 5). 이 게임에서는 저절로 성립한다 —
문진(問診)의 본질이 "들은 것을 파고드는 것"이기 때문이다.

#### ② 자유 타이핑 — 후보를 감춘다

입력창은 비어 있고, 아무 후보도 보이지 않는다.

이것이 드롭다운과의 결정적 차이다. **물을 수 있는 질문이 12개여도 화면에는 내가
떠올린 것만 보인다.** 드롭다운이면 12개를 다 눌러보게 되지만, 여기서는 4개만
떠올리고 8개는 존재조차 모른 채 계약한다. 그리고 결과 화면에서 이걸 본다:

> *"당신은 그가 직접 본 것인지 묻지 않았다. 마르타는 이웃에게 들은 이야기를
> 옮긴 것이었다."*

**떠올리지 못한 것에 대한 후회**는 드롭다운이 만들 수 없다. 안 누른 것은 내
선택이지만, 떠올리지 못한 것은 내 무능이다.

이것이 컨셉 문서의 *"성장하는 것은 캐릭터 스탯이 아니라 플레이어 자신의 안목"*을
문자 그대로 구현한다 — **회차를 거듭할수록 물을 줄 아는 질문이 늘어나는 것**이
곧 진행 시스템이다. 스탯은 하나도 오르지 않는데 플레이어는 확실히 강해진다.

#### ③ 자동완성 — guess the verb 지옥을 막는다

타이핑하면 후보 질문이 좁혀져 뜬다.

```
  ┌─────────────────────────────────────────┐
  │ 이상한 게 뭐│                            │
  ├─────────────────────────────────────────┤
  │ ▸ 정체를 묻는다                          │
  └─────────────────────────────────────────┘
```

Duskers 방식. 매칭은 **부분 문자열 포함**으로 충분하다 — `몇마리나`에도 `몇`이
있고 `규모가`에도 `규모`가 있으므로 한국어 형태소 분석이 필요 없다.

```ts
catalog.filter(q => q.keywords.some(k => input.includes(k)))
```

**핵심 안전장치: 매칭 실패는 대가가 없다.** 후보가 0개면 전송 자체가 안 되고
행동 횟수도 소모되지 않는다. 자유 입력의 유일한 진짜 위험(*"게임이 못 알아들었는데
내가 벌을 받았다"*)이 이것으로 제거된다. 입력창은 **탐색 도구**이고, 비용은
**실제로 던진 질문**에만 붙는다.

후보 0개가 몇 초 지속되면 **길드마스터북**을 펼칠지 묻는다. 책에는 종류별 필수
질문이 평문으로 적혀 있다 — **이 순간을 위해 그 서류가 존재한다.**

#### 질문 데이터의 모양

```json
{
  "id": "askScale",
  "slot": "scale",
  "label": "규모를 묻는다",
  "keywords": ["몇", "얼마", "규모", "수", "마리", "명", "크기", "덩치", "많", "정도"],
  "requires": { "slot": "target" },
  "line": "\"몇이나 됩니까?\""
}
```

`requires`가 대화를 자라게 한다 — 대상을 모르면 규모를 물을 수 없다. 키워드는
질문당 8~12개를 목표로 하고, 밸런싱 중 계속 추가한다 (데이터 파일이므로 코드를
건드리지 않는다).

### 4.4 처리량 압박 — 귀찮음을 선택으로 바꾸는 장치

**이것이 이 조사의 가장 중요한 결론이다.**

의뢰서 작성이 귀찮은 이유는 *"안 해도 되는데 해야 해서"*다. 꼼꼼히 하는 것이
항상 옳으면 그것은 결정이 아니라 세금이다 (원칙 3).

#### 실시간 시계는 쓰지 않는다

Papers, Please는 여권을 **대조**하는 게임이라 시계가 돌아도 된다. 이 게임은
**읽는** 게임이다. 화면에 초침이 돌면 플레이어는 텍스트를 안 읽고 넘긴다.
컨셉 문서가 *"텍스트가 지루하면 게임이 지루하다. 대체 채널이 없다"*고 적어둔
그 텍스트를, 아예 안 읽게 만드는 것이 더 나쁘다.

#### 시계를 턴제로 번역한다 — 하루의 행동 횟수

```
┌─ 3일차 ──────────────────── 남은 응대 ●●●●○○○○ ─┐
│                                                   │
│  마르타 (주민)                                     │
│  "발자국을 봤습니다. 커다란 발자국이요."            │
│                                                   │
│                              [질문한다]  [넘어간다] │
└───────────────────────────────────────────────────┘

  대기 중:  상인 길베르 · 관리 뒤랑 · 낯선 사람
```

- 질문 1회 = 1칸
- 협상 제안 1회 = 1칸
- 칸이 떨어지면 하루가 끝나고, **대기 중이던 사람들은 그냥 사라진다**

**읽는 시간에는 아무 압박이 없다.** 소모되는 것은 행동이지 실제 시간이 아니다.

| 플레이 방식 | 결과 |
|---|---|
| 한 건을 꼼꼼히 캐묻는다 | 의뢰서가 정확하다. 대신 그날 두 건밖에 못 받는다 |
| 대충 듣고 넘긴다 | 네 건을 받는다. 대신 위험도를 잘못 적을 확률이 오른다 |

**"이번 건은 대충 넘긴다"가 유효한 전략이 되는 순간 꼼꼼함은 노동에서 투자로
바뀐다.** 그리고 고정비(임대료·급여·치료비)가 그 압박을 실제로 만든다 —
처리량이 곧 생존이다.

#### 놓친 것이 보인다

대기 목록이 화면에 있으므로, 마르타에게 다섯 번 캐물으면 **관리 뒤랑을 오늘 못
부른다.** 그가 무슨 의뢰를 들고 왔는지는 **영원히 모른다** — 고보상 건이었을 수도
있고 함정이었을 수도 있다.

인내심 타이머 없이 "내가 이것을 포기했다"는 감정이 나오고, 톤도 깨지지 않는다.
기둥 5(*결정은 되돌아오지 않는다*)와도 맞물린다.

> **기존 시스템과의 구분**: `balance.json`의 `guildTiers.concurrentContracts`
> (등급별 2/3/4)는 **동시에 진행 중인 파견 수** 제한이지 접수 처리량 제한이
> 아니다. 두 개는 다른 축이며, 여기서 신설하는 것은 후자다.

### 4.5 반복 압축 — 후반이 초반보다 빨라야 한다

원칙 6. 세 장치를 쓴다:

1. **익숙한 서식은 미리 채워진다** — 같은 종류·같은 지역의 의뢰는 지난번 의뢰서를
   기본값으로 불러온다 (*"지난번 북쪽 숲 건과 같이"* 버튼)
2. **아는 의뢰인은 질문이 줄어든다** — 두 번째 만나는 의뢰인에게는 이미 아는 것을
   다시 묻지 않는다. 관계가 쌓이면 대화가 짧아진다
3. **판단 칸의 기본값을 제안한다** — 청취 결과에서 계산된 추천 등급이 회색으로
   미리 들어가 있다. **그대로 두는 것도 결정이다** (그리고 틀릴 수 있다)

3번은 조심해서 다뤄야 한다. 추천이 항상 맞으면 판단 칸이 사라진다. 추천은
**받아쓰기 칸만 보고 계산**하므로 소문으로 알아낸 것이나 의뢰인의 태도에서 읽은
것은 반영되지 않는다 — **추천을 이기려면 추천이 모르는 것을 알아야 한다.**

## 5. Obra Dinn 방식을 쓰지 않는 이유

Obra Dinn은 3개가 맞으면 즉시 확정해 준다. **이 게임은 그렇게 하면 안 된다.**

정답 판정이 즉시 오면 플레이어는 의뢰서를 맞을 때까지 고치게 되고, 그러면
**기둥 5(결정은 되돌아오지 않는다)가 무너진다.** 여기서 판정은 **파견 결과로
온다** — 결과 대조 화면이 Obra Dinn의 "확정" 순간에 해당하며, 그때는 이미
사람이 죽은 뒤다.

브루트포스 방지 장치도 필요 없다. **되돌릴 수 없으므로 시도 자체가 한 번뿐이다.**

가져오는 것은 하나뿐이다 — **피드백의 해상도를 낮춘다** (원칙 4). 결과 화면은
*"위험도를 낮게 적었다"*까지만 말하고 *"B였어야 했다"*는 말하지 않는다.
정확한 답을 알려주면 다음 회차에 계산이 되고, 이 게임은 계산이 아니라 판단을
요구한다.

## 6. 검증 기준 — 실패했는지 어떻게 아는가

플레이테스트에서 아래가 관측되면 이 설계는 실패한 것이다.

| 신호 | 무엇이 잘못됐나 | 첫 번째 노브 |
|---|---|---|
| 플레이어가 모든 질문을 다 한다 | 처리량 압박이 약하다 | 하루 행동 횟수 ↓ |
| 플레이어가 질문을 하나도 안 한다 | 오판의 대가가 약하다 | 위험도 오차 → 사망률 연동 ↑ |
| 판단 칸을 추천값 그대로 둔다 | 추천이 너무 정확하다 | 추천 계산에서 정보를 더 뺀다 |
| 특이사항을 항상 전부 붙인다 | 붙이는 비용이 없다 | 준비 시간 페널티 ↑ |
| 후보 0개가 자주 뜬다 | 키워드가 부족하다 | 질문당 키워드 추가 |
| 후반 클릭 수가 초반과 같다 | 반복 압축이 작동하지 않는다 | §4.5 장치 점검 |
| 대기 목록을 안 본다 | 놓친 것이 안 아프다 | 놓친 의뢰의 흔적을 소문으로 흘린다 |

## 7. 미해결 질문

1. **위험도 등급을 몇 단계로 할 것인가?** 기획서는 D/C/B/A/S 5단계다. 현재
   구현은 0~200 연속값이므로 매핑 규칙이 필요하다. 단계가 많으면 판단이 정밀해지고
   적으면 뭉툭해진다 — 뭉툭한 쪽이 "판단"에 가깝다.
2. **모험가가 의뢰서를 읽고 어떻게 반응하는가?** 위험도를 높게 적으면 배정을
   거부할 수 있는가? 그러면 낮게 적을 유인이 생긴다 — **이것은 의도된 부패인가?**
   (설계 의도로는 그렇다. 확인 필요)
3. **특이사항 토큰의 타입을 몇 종으로 할 것인가?** Golden Idol은 4색을 썼다.
4. **길드마스터북을 언제 처음 보여주는가?** 온보딩의 일부인가, 막혔을 때만
   나타나는가?
5. **하루 행동 횟수는 무엇으로 늘어나는가?** 길드 등급인가, 접수원 고용인가,
   아니면 고정인가? 늘어나지 않으면 후반에 성장 감각이 없고, 너무 늘면 압박이
   사라진다.
