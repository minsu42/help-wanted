## Overview

**의뢰서는 플레이어의 판단이 문서가 되어 남의 손에 들어가는 곳이다.**

청취(#21)가 알아낸 것을 좁혀 주면, 의뢰서는 그것을 두 종류의 칸에 나눠 담는다 —
**받아쓰기 칸**은 청취 결과가 자동으로 옮겨지고 플레이어가 고칠 수 없으며,
**판단 칸**은 플레이어가 직접 적는다. 위험도 등급 · 권장 인원 · 특이사항이 판단 칸이다.

그리고 **모험가는 의뢰서에 적힌 대로 준비하고 출발한다.** 실제 위험이 아니라 **적힌
위험**이 준비도를 정한다. 낮게 적으면 값을 덜 치르고 아무도 거부하지 않지만, 준비가
모자란 채로 간다. 이 한 문장이 기둥 6의 전부이며, 이 시스템이 존재하는 유일한 이유다.

### 이 시스템이 없으면

청취가 알아낸 것이 **자동으로** 파견 판정에 반영된다. 그러면 결과가 나빠도 시스템 탓이고,
*"내가 C급이라고 적었다"* 가 나오지 않는다 — Core hypothesis가 검증할 문장이 사라진다.

### 경계 — 무엇이 이 문서의 것이 아닌가

| | 소유 |
| ---- | ---- |
| 슬롯 상태·`limiter`·`completeness` 계산 | **청취 (#21)** — 의뢰서는 **읽기만** 한다 |
| 적힌 위험도가 파견 결과를 어떻게 바꾸는가 | **파견 판정 (#10, P2)** |
| 3단 대조 화면(알았던 것/적은 것/실제) | **결과 대조 (#11, P2)** |
| 흥정에서 근거로 쓰이는 방식 | **계약 협상 (#9, P3)** |

**이 문서가 소유하는 것은 「칸의 정의」와 「등급 매핑」과 「추천 계산」 셋이다.**

## Detailed Rules

### R1. 칸은 두 종류다. 섞이지 않는다

| | 받아쓰기 칸 | 판단 칸 |
| ---- | ---- | ---- |
| 무엇 | 종류 · 대상 · 규모 · 장소 · 기한 · 경로 (열린 슬롯만) | **위험도 등급 · 권장 인원 · 특이사항** |
| 누가 채우나 | **청취가 자동으로** | **플레이어가 직접** |
| 고칠 수 있나 | **아니오** | 예 (도장 전까지) |
| 틀릴 수 있나 | 아니오 — 알아낸 것을 그대로 옮긴다 | **예. 그것이 핵심이다** |

> **왜 받아쓰기 칸을 못 고치게 하는가**: 고칠 수 있으면 *"트롤 3마리"* 를 *"고블린
> 1마리"* 로 바꿔 적을 수 있고, 그 순간 이 게임은 **거짓 서류 작성 게임**이 된다.
> 거짓말은 **판단 칸에서만** 가능해야 한다 — 위험도를 낮춰 적는 것은 거짓이 아니라
> **판단**이며, 그 구별이 기둥 6이 억울함이 되지 않게 막는다.

### R2. 판단 칸을 비워도 도장을 찍을 수 있다

막다른 길 금지(기둥 5)는 의뢰서에도 적용된다. 다만 **빈 칸은 기본값이 아니라 빈 칸으로
파견에 전달된다** — 위험도 미기재는 *"위험 없음"* 이 아니라 *"모른다고 적었다"* 이고,
모험가는 그것을 보고 각자 알아서 판단한다 (구체 효과는 P2 소유).

### R3. 등급은 뭉툭하다 — 숫자를 적지 않는다

플레이어는 위험도를 **D/C/B/A/S 다섯 등급 중 하나로** 적는다. 0~200 원시값은
**화면에 나가지 않는다** (`Adventurer.capability`를 숨기고 `Grade`만 내보내는 기존 규약과
같다 — `types.ts`).

> **뭉툭할수록 판단에 가깝다.** 숫자를 적게 하면 최적화가 되고, 최적화는 판단이 아니다.

## Formulas

### F1. 위험도 등급 매핑 (`gradeOfRisk`)

```
risk → 'D' | 'C' | 'B' | 'A' | 'S'
```

| 등급 | `risk` | 뜻 — **필요한 파티** |
| ---- | ---- | ---- |
| **D** | < 40 | 혼자서도 된다 |
| **C** | 40 ~ 79 | 둘이면 안전하다 |
| **B** | 80 ~ 119 | 셋이 필요하다 |
| **A** | 120 ~ 169 | 셋 + 숙련 이상 |
| **S** | ≥ 170 | 정예 셋이 아니면 죽는다 |

**밴드를 파티 구성으로 정한 것이 이 표의 핵심이다.** 등급은 추상적인 위험 눈금이 아니라
*"몇 명을, 어느 수준으로 보내야 하는가"* 를 뜻해야 한다 — 그것이 모험가가 의뢰서를 읽고
준비하는 방식이기 때문이다 (기둥 6).

**실측 근거** (`balance.json`):
`dispatch.successRatio = 1.0`이므로 **파티 역량 합 ≥ 위험도**면 성공이 확정된다.
`adventurer.gradeThresholds`는 steady 25 / skilled 50 / veteran 75이고 파티 상한은 3명
(`scaling.maxPartySizeCap`)이다.

| 등급 | 필요 역량 합 | 실제로 되는 조합 |
| ---- | ---- | ---- |
| D (<40) | <40 | steady 1명 (25~50) |
| C (40~79) | ~80 | steady 2명 (50~100) |
| B (80~119) | ~120 | steady 3명 (75~150) 또는 skilled 2명 |
| A (120~169) | ~170 | skilled 3명 (150~225) |
| S (≥170) | 170+ | veteran 3명 (225~270) |

**밴드 폭이 40으로 균일한 것도 우연이 아니다** — `scaling.riskSpread = 0.2`이므로 명성
50 구간(기대 위험도 102.5)에서 흔들림이 ±20.5, **거의 정확히 한 밴드**다.

> **그래서 오차의 질감이 이렇게 갈린다:**
> - **1밴드 오차** — 무작위성에서 온다. 흔하고, 대개 부상으로 끝난다
> - **2밴드 오차** — 은폐에서 온다. `scaling.concealmentMax = 0.45`이므로 의뢰인의
>   주장은 실제의 55%까지 내려갈 수 있고, 그것은 **두 밴드 아래**다. 사람이 죽는다
>
> 밸런싱하지 않았는데 이렇게 나왔다. **은폐를 뚫는 것이 곧 사람을 살리는 것**이라는
> 관계가 숫자로 이미 성립해 있다.

**경계 처리**: 상한 없음. 명성 100 + 유혹 의뢰(`temptationRiskMultiplier = 1.6`)면
위험도가 200을 넘는다(최대 ~326). `S`가 열린 등급이므로 문제가 없지만,
**`scales.risk`의 주석 *"0~200"* 은 실제로는 상한이 아니다** — 데이터 문서를 정정할 것.

## 지금 열려 있는 결정

### ⚠ D1. 슬롯 내용이 위험도 추정으로 어떻게 이어지는가 — **가장 큰 갈림길**

추천 등급을 계산하려면 *"알아낸 것"* 이 *"위험하다"* 로 번역돼야 하는데, **그 다리가
어디에도 없다.** 슬롯은 `대상=트롤` 같은 **내용**이고 위험도는 **숫자**다.

- **(가) `completeness`만 쓴다** — 추천은 `statedRisk`를 등급으로 바꾼 것이고,
  `completeness`는 신뢰 폭만 정한다. 데이터 추가 없음. **그러나 슬롯 *내용*이 추천에
  아무 영향이 없어서, 무엇을 알아냈든 같은 추천이 나온다**
- **(나) 슬롯 진값이 위험 기여도를 갖는다** — `quest-templates.json`의 슬롯 값마다
  위험 델타(`대상=트롤 → +30`). 알아낼수록 추정이 실제에 가까워진다. **데이터가 늘고
  콘텐츠 작성량이 생긴다**
- **(다) 하이브리드** — 기여도는 두되 `completeness`가 노출 정도를 정한다

이것은 **청취 GDD의 미해결 Q2(F5 가중치가 공략집이 된다)와 같은 뿌리**다. Q2는 P2 스펙의
숙제로 넘겨 뒀는데, **추천 계산이 그것을 P1으로 당겨온다.**

### ⚠ D2. 특이사항 토큰은 어디서 오는가

*"야간"* *"수중"* *"독"* 같은 토큰이 판단 칸의 셋째 항목인데 출처가 정해져 있지 않다 —
슬롯에서 파생되는가, 소문에서 오는가, 고정 목록에서 플레이어가 고르는가.
`paperwork-ux`가 *"타입 제약 토큰"* 을 클릭 노동 방어책으로 지목하고 있어 **1순위 리스크에
직접 물린다.**

### D3. Q7은 이 문서에서 답했다 — **5등급 D/C/B/A/S** (F1)

청취 GDD의 Open Question Q7이 여기로 넘어와 있었고, `balance.json` 실측으로 밴드를
파티 구성에 맞춰 정했다. **청취 GDD의 Q7을 해소로 표시할 것.**
