## Context

### 왜 지금인가

캠페인이 **8~15시간**이고 세션이 30~60분이다. 한 탭에서 끊지 않고 8시간을 하는 사람은
없으므로 **지속성은 선택이 아니라 필수다.** 그런데 컨셉·로드맵 어디에도 저장이 없었다
(2026-08-09 정합성 감사에서 발견).

**저장 포맷은 모든 스키마 변경에 물린다.** ADR-001이 방금 `Contract`를 재설계했고
`ReadonlyMap`을 들여왔다. **지금 잡지 않으면 P3 이후에 그때까지의 모든 스키마를 소급
마이그레이션해야 한다.** 그리고 지금은 **세이브 파일이 세상에 하나도 없다** — 마이그레이션
비용이 정확히 0인 유일한 시점이다.

### 이미 정해져 있는 것 (이 ADR의 입력)

| 결정 | 소유 문서 |
| ---- | ---- |
| 재현 키는 **분류 결과 `(노드 id, 화법)`** (타이핑 원문도, 클릭 앵커도 아니다) *(2026-08-10 정정 — 옛 「매칭된 질문 id」는 질문 카탈로그 모델의 것이고, 3차 개정이 그 모델을 폐기했다. ADR-003 D4와 같은 결정)* | `intake-system.md` 「결정론」 |
| **로그 재생(replay) 방식 기각** — 재생 순서가 어긋나면 최종 상태가 갈린다. 그리고 **3차 개정 이후 근거가 더 강해졌다**: 재생하려면 타이핑 원문을 다시 분류해야 하는데 **LLM 분류는 재현이 보장되지 않는다** | 같은 절 |
| 단일 슬롯 자동 저장 · 저장 시점은 **하루 마감뿐** | `game-concept.md` 「지속성」 |
| 서버 없음은 **영구 제약** (NAN2026 예선 · GitHub Pages) | `roadmap.md` 「배포 채널」 |

### 조사에서 나온 것 — ⚠ `Rng`를 저장할 방법이 없다

```ts
export function createRng(seed: number): Rng {
  let state = seed >>> 0;          // ← 클로저에 갇혀 있다
  const next = () => { state = (state + 0x6d2b79f5) >>> 0; /* … */ };
  return { next, int, range, chance, pick };   // ← state를 내보내지 않는다
}
```

`Rng`는 `next`/`int`/`range`/`chance`/`pick`만 노출한다. **현재 상태를 읽을 수도, 특정
상태로 되돌릴 수도 없다.**

컨셉 문서는 *"시드와 결정 로그를 함께 저장한다"* 고 적었는데, **mulberry32의 N번 뽑은 뒤
상태는 시드가 아니다.** 시드만 저장하면 복원 시 세계가 처음으로 되감긴다. 즉 **현재
API로는 세이브가 원리적으로 불가능하다.**

이것은 기존 도메인 모듈의 공개 API 변경이므로 이 ADR이 다룬다.

## Decision

### D1. `Rng`에 `snapshot()`을 추가한다 — 새 팩토리는 필요 없다

```ts
export interface Rng {
  // ... 기존 5개 그대로 ...
  /**
   * 현재 내부 상태. **저장·복원 전용이며 게임 로직이 읽어선 안 된다.**
   *
   * `createRng(rng.snapshot())`이 정확히 이 지점부터 이어지는 생성기를 만든다 —
   * mulberry32의 상태가 32비트 정수 하나이고 `createRng`가 그것을 그대로 초기 상태로
   * 삼기 때문이다. 별도의 `restoreRng`가 필요 없는 이유가 이것이다.
   */
  snapshot(): number;
}
```

구현은 한 줄이다 (`snapshot: () => state`). **복원은 `createRng(saved.rngState)`** 이며
새 함수를 만들지 않는다.

> **왜 이것이 정확한가**: `createRng(s)`는 `state = s >>> 0`으로 시작하고, 첫 `next()`가
> `state + 0x6d2b79f5`를 계산한다. 상태 `s_k`에서 저장하고 `createRng(s_k)`로 복원하면
> 다음 뽑기가 동일하게 `s_k + 0x6d2b79f5`가 된다. **뽑은 횟수를 셀 필요가 없다.**

### D2. 최종 상태를 직접 저장한다. 로그는 감사용 부가 데이터다

재생 방식을 기각한 결정(`intake-system.md`)을 포맷 수준에서 못박는다.

- 슬롯 상태·**사유(무지/은폐)**·자금·신뢰·기억 — **전부 값 그대로 저장한다**
  *(2026-08-10: 옛 `limiter`는 3차 개정에서 F2의 「사유」로 대체됐다)*
- 감사 로그(`{타이핑 원문, 분류 결과, 경로: llm|fallback}`)는 **저장하되 복원에 쓰지
  않는다.** 버그 재현과 사후 분석용이다
- 따라서 `quest-templates.json`의 **폴백 키워드**를 밸런싱으로 바꿔도 **과거 세이브의
  슬롯 상태가 변하지 않는다** (GDD AC-DET-03)
  *(2026-08-10: `questions.json`은 3차 개정에서 폐기됐다)*

### D3. 도메인 타입을 그대로 직렬화하지 않는다 — 명시적 DTO를 둔다

```ts
// src/domain/save.ts — 순수 함수. localStorage를 모른다
export const SAVE_SCHEMA_VERSION = 1;

export interface SaveFileV1 {
  readonly schemaVersion: 1;
  readonly savedOnDay: number;
  readonly rngState: number;
  readonly state: GameStateDtoV1;
}

export function toSave(state: GameState): SaveFileV1;
export function fromSave(file: SaveFileV1, config: GameConfig): GameState;
```

**`JSON.stringify(gameState)` + replacer/reviver 방식을 기각했다.**

> 편해 보이지만 **도메인 타입에 필드를 하나 추가하면 저장 포맷이 조용히 바뀐다.**
> 이 저장소는 조용한 드리프트로 이미 여러 번 다쳤다 — 문서가 "Vite 5.4"라고 적는 동안
> 실제로는 7.3.6이 돌고 있었고, 테스트 407개가 통과하는 동안 결과 대조 화면이 주 동선에서
> 통째로 빠져 있었다.
>
> 명시적 DTO는 **도메인 타입이 바뀌면 매핑 함수가 컴파일 에러를 낸다.** 스키마 변경을
> 사람이 알아채는 것이 아니라 **컴파일러가 강제하게** 만드는 것이 이 결정의 전부다.

`Map`/`Set`은 DTO에서 배열로 편다:

| 도메인 | DTO |
| ---- | ---- |
| `ReadonlyMap<SlotName, SlotTruth>` (ADR-001) | `[SlotName, SlotTruth][]` |
| `ReadonlyMap<string, SlotProgress>` | `[string, SlotProgress][]` |
| `ReadonlySet<string>` (`revealedFacts` 등) | `string[]` |
| `Set<string>` (`usedNames`, `talkedToday`) | `string[]` |
| `Rng` | `number` (D1) |

### D4. 설정은 저장하지 않는다

`GameConfig`(= `balance.json`)와 `names.json`은 **세이브에 들어가지 않는다.**
`fromSave(file, config)`가 현재 설정을 주입받는다.

**대가를 명시한다**: 밸런스 패치가 **기존 세이브에 소급 적용된다.** 길드 등급 비용이
바뀌면 이미 진행 중인 회차의 비용도 바뀐다.

> 그래도 이쪽을 고르는 이유: 반대로 하면 **낡은 밸런스가 세이브에 화석처럼 굳는다.**
> 이 프로젝트는 밸런싱이 P8까지 계속되고 예선 제출 빌드가 언제 찍힐지 모른다 — 패치가
> 안 먹는 세이브가 더 나쁜 버그다. 그리고 `balance.json` 격리 원칙(하드코딩 금지)의
> 취지가 *"한 곳만 고치면 전부 반영된다"* 이므로 세이브가 그것을 깨서는 안 된다.

### D5. 저장 시점은 하루 마감뿐. 슬롯 하나. 자동.

- 하루가 끝날 때(`advanceDay` 직후) 한 번 쓴다. 그 외 저장 지점은 **없다**
- 슬롯 하나를 덮어쓴다. 수동 저장·이름 붙인 슬롯·분기 저장 **없음**
- 키: `helpWanted.save.v1` (스키마 버전을 키에 넣어 v2와 공존 가능하게 한다)

### D6. 세이브 스캐밍 — 막지 않는다. **무의미하게 만든다.**

정적 호스팅이라 서버 검증이 불가능하고, `localStorage`는 복사할 수 있다. **막을 수 있는
척하지 않는다.** 대신 D1+D5의 조합이 다음 성질을 공짜로 준다:

> **하루 마감 세이브를 다시 불러 같은 결정을 하면 결과가 바이트 단위로 같다.**

RNG 상태를 함께 저장하므로 파견 판정·의뢰 생성·홀 출석이 전부 동일하게 재현된다.
**되감아서 주사위를 다시 굴리는 것은 불가능하다.**

남는 것은 하나뿐이다 — 하루를 통째로 다시 플레이하며 **결정을 바꾸는 것.** 그것은
비용(30~60분 재플레이)이 크고, 저장 지점이 하루 경계뿐이라 *"방금 그 파견만 다시"* 가
안 된다.

| 하고 싶은 것 | 가능한가 |
| ---- | ---- |
| 파견 결과만 다시 굴리기 | **불가능** — RNG 상태가 같다 |
| 흥정 결과만 다시 굴리기 | **불가능** — 판정에 난수가 없다 (`negotiation.ts`) |
| 하루를 다시 플레이하며 다른 결정 | 가능. **막지 않는다** |

> 기둥 5(*결정은 되돌아오지 않는다*)와의 충돌은 **완전히 해소되지 않는다.** 이 ADR은
> 그 사실을 숨기지 않고, *"싸고 즉각적인 되감기"* 만 제거한다. 정적 호스팅에서 가능한
> 최선이다.

### D7. 실패는 게임을 멈추지 않는다

| 상황 | 동작 |
| ---- | ---- |
| `schemaVersion`이 모르는 값 | **불러오지 않는다.** 파일을 지우지도 않는다. 새 회차로 시작하고 사용자에게 알린다 |
| JSON 파싱 실패 · 필수 필드 누락 | 위와 같다. **부분 복원을 시도하지 않는다** |
| 저장 실패 (용량 초과·시크릿 모드) | **게임은 계속된다.** 조용히 삼키지 않고 한 번 알린다 |

**부분 마이그레이션을 하지 않는다.** 반쯤 복원된 상태는 재현 불가능한 버그의 원천이고,
이 게임은 결정론이 기둥이라 그것이 특히 비싸다.

### D8. 계층 — 순수 변환과 I/O를 가른다

```
src/domain/save.ts          순수. toSave / fromSave / DTO 타입. localStorage를 모른다
src/presentation/…          localStorage 어댑터 (읽기·쓰기·예외 처리)
```

`src/domain/**`는 파일 I/O도 브라우저 API도 몰라야 한다 —
`.claude/docs/coding-standards.md`의 *"단위 테스트는 외부 API·파일 I/O를 호출하지 않는다"*
와 기존 도메인 규약(`Rng` 주입, 순수 함수)을 그대로 따른다.

### D9. 휘발 상태를 명시한다 — 청취의 런타임 구조는 저장하지 않는다 *(2026-08-10 신설)*

**저장하지 않는 것 셋**을 결정으로 못박는다. 지금까지는 *"안 적혀 있는 것"* 이었고,
안 적혀 있으면 구현자가 넣게 된다.

| 상태 | 무엇 | 저장 |
| ---- | ---- | ---- |
| **그물 인스턴스** | 노드 방문 여부, 게이트 잠김/열림, 무지 종단 실현 결과 | ❌ |
| **청취록** | 이번 의뢰인의 문답·기색 기록 (GDD V4·U5) | ❌ |
| **분류 캐시** | `NFC(원문) → (노드, 화법)` (GDD R10) | ❌ |
| 슬롯 상태 + **사유** | `미상`/`막힘(무지)`/`막힘(은폐)`/`모호`/`확정` | ✅ **D2대로 값으로 저장** |

#### 왜 저장할 필요가 없는가 — D5로부터 따라 나온다

```
D5:  저장 시점은 하루 마감뿐
컨셉: 칸이 떨어지면 하루가 끝나고 대기 중이던 의뢰인들은 그냥 사라진다
GDD:  같은 의뢰인이 다시 와도 이번 계약의 그물은 새로 구워진다
────────────────────────────────────────────────────────────
∴    저장이 일어나는 순간, 창구에 앉아 있는 사람이 없다
∴    그 순간 그물·청취록·캐시는 이미 소멸했다 — 건널 경계가 없다
```

**도장을 찍은 뒤 배정·파견으로 넘어가는 것은 슬롯 상태와 의뢰서 내용이지 그물이
아니다.** 결과 대조(P2)가 요구하는 `미상`/`막힘` 구별도 슬롯 상태이며, 둘 다 D2가
이미 값으로 저장한다. **하류의 누구도 그물 자체를 필요로 하지 않는다.**

#### 이 결정이 실제로 사는 값 — LLM 비결정성이 세이브에 닿지 않는다

**이것이 D9의 진짜 이유다.** ADR-003이 런타임 LLM을 들이면서 *"세이브가 비결정성에
오염되지 않는가"* 가 열렸다. D9가 그 질문을 **구조적으로** 닫는다:

> **세이브에 들어가는 값 중 LLM이 만든 것은 하나도 없다.**
> 슬롯 상태는 분류 결과를 입력으로 받은 **순수 함수의 출력**이고, 저장되는 것은
> 그 출력이지 입력이 아니다. 분류·연기·캐시는 전부 하루 안에서 나고 죽는다.

따라서 **모델을 바꾸든, 프롬프트를 고치든, 폴백 모드로 완주하든 과거 세이브는
흔들리지 않는다.** GDD의 AC-DET-03이 검증하는 성질이 여기서 나온다.

#### 대가 — 하루를 중간에 끊으면 그날이 통째로 날아간다

숨기지 않는다. 브라우저를 닫으면 **그날 한 청취가 전부 사라진다.**

> 그래도 이쪽인 이유: **중간 저장을 넣는 순간 D6이 무너진다.** D6의 유일한 방어는
> *"되감으려면 하루를 통째로 다시 해야 한다"* 이고, 저장 지점이 하루 경계뿐이라
> *"방금 그 파견만 다시"* 가 불가능하다는 것이 그 성질의 전부다. 중간 저장은
> 정확히 그 문을 연다. **휴대성과 스캐밍 방어 중 후자를 고른 것이 D5·D6이었고,
> D9는 그 선택을 청취 쪽에서 재확인할 뿐 새 선택이 아니다.**
>
> 완화는 설계가 이미 하고 있다 — 세션 길이가 30~60분이고 **하루 마감이 자연
> 정지점**이라(컨셉), 하루 ≈ 한 세션이다.

#### ⚠ 이 결정이 깨지는 조건

**하루 중간 저장이 도입되면 D9는 즉시 무효다** — 그때는 그물·캐시 스키마가 실제로
필요하고, **D6(스캐밍 방어)을 어떻게 지킬지부터 다시 설계해야 한다.** D9만 고쳐서는
안 된다. 다음 사람에게: **이 문단이 D9와 D6이 한 몸이라는 증거다.**

## Alternatives Considered

| 안 | 왜 기각했나 |
| ---- | ---- |
| **시드 + 결정 로그를 재생해 복원** (컨셉 문서의 원안) | `intake-system.md`가 이미 기각했다 — 재생 순서가 어긋나면 최종 상태가 갈리고, 카탈로그가 바뀌면 과거 세이브가 깨진다. 그리고 **재생은 8시간 캠페인에서 복원 시간이 선형으로 증가한다** |
| **`JSON.stringify` + replacer/reviver** | 도메인 필드를 추가하면 저장 포맷이 **조용히** 바뀐다. D3의 기각 기록 참조 |
| **`Rng`에 `restoreRng(state)` 별도 팩토리 추가** | 불필요하다. `createRng(snapshot())`이 정확히 같은 일을 한다 (D1). API를 늘리지 않는 쪽을 택한다 |
| **뽑은 횟수(`drawCount`)를 저장하고 복원 시 그만큼 공회전** | 8시간이면 수만~수십만 회다. 복원이 느려지고, 무엇보다 **`snapshot()` 한 줄로 끝나는 일을 우회하는 것**이다 |
| **설정(`balance.json`)을 세이브에 포함** | 낡은 밸런스가 세이브에 굳어 패치가 안 먹는다. D4 참조 |
| **여러 슬롯 / 수동 저장** | 스캐밍을 **초대하는** 구조다. 분기 저장이 있으면 D6의 유일한 방어(재플레이 비용)가 사라진다 |
| **매 행동마다 자동 저장** | 같은 이유. 그리고 하루 경계가 아니면 *"방금 그 파견만 다시"* 가 가능해진다 |
| **분류 캐시를 세이브에 포함** *(2026-08-10 — 설계 리뷰가 제안한 방향)* | **불필요하다.** 저장 시점(하루 마감)에 창구에 사람이 없으므로 캐시가 건널 경계가 없다 (D9). 리뷰의 지적(*"수명이 미정의"*)은 옳았으나 답이 반대였다 — 넣는 것이 아니라 **안 넣는다고 적는 것**이 답이다. 넣으면 세이브가 커지고, 없어도 되는 필드가 스키마에 남아 D3의 "매핑 함수가 컴파일 에러를 낸다"는 이득이 무의미한 곳까지 확장된다 |
| **그물 인스턴스를 세이브에 포함** *(2026-08-10)* | 같다 (D9). 하류(배정·파견·결과 대조)가 필요로 하는 것은 **슬롯 상태와 사유**뿐이고 그것은 D2가 이미 값으로 저장한다. 그물을 저장하면 **`quest-templates.json` 변경 시 과거 세이브가 깨지는 경로가 새로 생긴다** — AC-DET-03이 막으려던 바로 그것이다 |

## Consequences

### 좋아지는 것

- 8~15시간 캠페인이 실제로 완주 가능해진다 — **P7(메인 스토리 3막)의 전제 조건이다**
- **파견 결과를 되감을 수 없다**는 강한 성질이 RNG 스냅샷에서 공짜로 나온다
- 스키마 변경이 컴파일 에러가 되므로 조용한 포맷 드리프트가 구조적으로 막힌다
- `Rng.snapshot()`은 **디버깅에도 쓴다** — 버그 신고에 시드 대신 상태를 첨부하면
  임의 시점을 정확히 재현할 수 있다

### 대가와 위험

1. **`Rng` 인터페이스가 바뀐다.** 구현체가 하나뿐이라 변경은 작지만, `Rng`를 목으로
   만드는 테스트가 있으면 `snapshot`을 추가해야 한다
2. **DTO 매핑을 손으로 쓴다.** `GameState`가 12필드 + 중첩 객체이므로 초기 작성량이 있다.
   **그것이 이 결정이 사는 값이다** — 자동화하면 D3의 이유가 사라진다
3. **⚠ `Client`는 `Contract` 안에만 존재한다.** 의뢰가 끝나면 의뢰인도 사라지므로
   *"예전에 왔던 마르타"* 를 세이브가 기억하지 못한다. P1에서는 문제가 없지만
   **P6(길드 장부 과거 기록 조회)에서 스키마가 한 번 더 바뀐다.** 지금 미리 만들지
   않는다 — 추측으로 필드를 넣지 않는 것이 이 프로젝트의 규약이다
4. **밸런스 패치가 진행 중인 세이브에 소급 적용된다** (D4). 의도된 것이지만, 예선 제출
   직전에 밸런스를 만지면 심사자의 진행 중 세이브가 영향을 받는다
5. **세이브 크기는 문제가 아니다.** 명부 수십 명 + 의뢰 몇 건 + 집합 몇 개면 수십 KB
   수준이고 `localStorage`는 통상 5MB다. **초기 로드 예산과 무관하다** (세이브는 번들이
   아니다)

### 되돌리는 법

`src/domain/save.ts`와 어댑터를 지우면 된다. `Rng.snapshot()`은 남겨도 무해하다 —
게임 로직이 읽지 않기 때문이다.

## Verification

| 무엇 | 어떻게 |
| ---- | ---- |
| **왕복 항등** — `fromSave(toSave(s), config)`가 원본과 같은 상태를 만든다 | 단위 테스트. `Map`/`Set`이 배열로 폈다가 정확히 복원되는지 포함 |
| **RNG 이어짐** — 저장 후 복원한 생성기가 저장 안 한 생성기와 **같은 수열**을 낸다 | `createRng(rng.snapshot())`과 원본을 각각 100회 뽑아 비교 |
| **되감기 무의미** — 하루 마감에서 저장 → 하루 진행 → 복원 → 같은 결정으로 하루 진행, **두 결과가 동일** | 통합 테스트. D6의 핵심 주장을 증명하는 유일한 테스트다 |
| **슬롯 상태가 폴백 키워드·템플릿 변경에 안 흔들린다** | GDD **AC-DET-03** (지금까지 스텁이었다 — **이 ADR로 실테스트 승격 가능**) |
| **`미상`/`막힘(+사유)` 구별이 직렬화를 넘어 보존된다** | GDD **AC-CORE-02 · AC-CORE-04** *(2026-08-10: 3차 개정에서 AC 번호가 재배치됐다)* |
| 모르는 `schemaVersion`을 만나면 크래시 없이 새 회차로 | 단위 테스트 |
| `src/domain/**`에 `localStorage`가 없다 | 정적 검사 *(2026-08-10: 옛 참조 「AC-R9-01과 같은 방식」을 지웠다 — GDD 3차 개정에서 그 번호가 **화법 소비처 검증**으로 재배정되어 가리키는 것이 달라졌다)* |
| **D9 — 세이브에 그물·청취록·캐시가 없다** *(2026-08-10 신설)* | `SaveFileV1` 타입에 해당 필드가 **없음**을 정적으로 확인. 그리고 왕복 테스트에서 그물을 진행시킨 뒤 저장·복원했을 때 **슬롯 상태만 살아남고 그물이 비어 있는지** |
| **D9 — LLM이 만든 값이 세이브에 없다** *(2026-08-10 신설)* | 게이트웨이 목을 **서로 다른 두 응답 집합**으로 바꿔 가며 같은 `(노드, 화법)` 시퀀스를 재생 → **세이브 바이트가 동일**해야 한다. D9의 핵심 주장을 증명하는 유일한 테스트다 |

> **GDD의 AC-DET-03을 스텁에서 뺄 수 있게 됐다.** 그 AC는 *"`persistence` 스펙 확정
> 전까지 스텁"* 이었고, 이 ADR이 그 스펙이다. `intake-system.md`의 해당 주석을 갱신할 것.
