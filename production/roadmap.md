## 이 문서를 읽는 법

**날짜가 없다.** 시간 제약을 해제했으므로 일정 대신 **순서와 의존 관계**로 계획한다.
각 단계는 앞 단계가 끝나야 시작할 수 있고, 완료 기준을 통과해야 다음으로 간다.

각 단계는 이렇게 적혀 있다:

- **왜 이 순서인가** — 앞뒤가 바뀌면 무엇이 무너지는가
- **들어가는 것** — 구현 항목
- **완료 기준** — 이걸 못 보이면 안 끝난 것이다
- **먼저 쓸 문서** — 구현 전에 필요한 스펙

## 전체 구조

```
  P0 정리
   │
   ├─ P1 청취 + 의뢰서          ─┐
   ├─ P2 책임 (의뢰서 → 결과)    ├─ 세로 슬라이스
   └─ P3 압박 (처리량 + 고정비)  ─┘
   │
  ╔═══════════════════════════════╗
  ║  GATE — Core Hypothesis 검증  ║   ← 여기서 게임의 생사가 갈린다
  ╚═══════════════════════════════╝
   │
   ├─ P4 사람 (가치관·관계·상실)
   ├─ P5 세력 평판
   ├─ P6 세계 변화
   ├─ P7 메인 스토리 3막
   └─ P8 폴리시 · 오디오 · 접근성
```

**P1~P3이 세로 슬라이스다.** 여기까지 만들고 플레이테스트해서 Core hypothesis를
검증한 뒤에 P4 이후로 간다. **게이트를 건너뛰지 않는다** — P6(세계 변화)은 가장
비싼 단계인데, 창구가 재미없으면 그 비용이 전부 낭비된다.

## 경진대회 제출에 대하여 (2026-08-09 결정)

### 배포 채널 — **GitHub Pages 고정. 재검토하지 않는다.**

**이 프로젝트는 NAN2026 예선 제출용이다.** 배포는 무조건 GitHub Pages다.

이 결정이 닫는 것:

- ~~**「넘을 수 없는 제약」 1번(서버가 없다)은 영구 제약이다.** 런타임 LLM 호출·서버측
  검증·커스텀 HTTP 헤더(COOP/COEP, 따라서 SharedArrayBuffer·WASM 멀티스레드)는
  **재검토 대상이 아니다.**~~ → **부분 번복 (2026-08-10, ADR-003).** 사용자 결정으로
  **런타임 LLM이 전용 프록시(Cloudflare Worker) 경유로 도입된다.** 게임 본체는 여전히
  Pages이고, 프록시는 무상태 LLM 중계일 뿐 게임 서버가 아니다 — 따라서 서버측 세이브
  검증·커스텀 헤더(COOP/COEP)는 **여전히 불가능하고**, 세이브 스캐밍 방어도 그대로
  *"금지가 아니라 무의미하게 만든다"* 뿐이다 (ADR-002 D6).
- 시장조사(`design/research/interrogation-games-market-2026-08-09.md` §2)가 열어 둔
  *"Steam이면 웹 전제를 재검토할 수 있다"* 는 **소멸했다.**
- `vite.config.ts`의 **`base: "./"`** 는 영구 필수 설정이다.

### ⚠ 그런데 이 결정이 새 리스크를 만든다 — 심사자는 완주하지 않는다

**캠페인은 8~15시간인데, 예선 심사에서 실제로 플레이되는 것은 첫 20~30분이다.**

로드맵의 P1~P3 → GATE 순서는 *"이 게임이 재미있는가"* 를 검증하는 순서이고, 그건 옳다.
그러나 **그것은 *"첫 30분이 심사에서 이기는가"* 를 검증하는 순서가 아니다.** 둘은 다른
질문이며, 지금 이 문서는 후자를 어디서도 묻지 않는다.

이미 있는 부분적 방어 두 개:
- 아래 **「제출용 단계를 따로 두지 않는다」 + 「`main`은 항상 배포 가능」** — 아무 날에
  마감이 와도 내보낼 것이 있다
- **첫 화면 1초 / 초기 전송 1MB 예산** — 심사자는 링크를 열고 로딩을 기다려 주지 않는다.
  `technical-preferences.md`의 성능 예산이 여기서 **심사 리스크**가 된다

**부족한 것 — 각 단계의 완료 기준에 넣을 것:**

> **첫 세션(1일차)이 그 자체로 완결된 인상을 주는가.**
> 8~15시간의 1/30만 보고 판단하는 사람에게 *"이 게임이 무엇인지"* 가 전달되어야 한다.

P1의 마르타 시나리오가 사실상 이 역할을 하고 있으므로 구조는 이미 있다. **명시되지
않았을 뿐이다** — GATE 통과 기준에 *"처음 30분만 플레이한 사람도 Core hypothesis 문장을
말할 수 있는가"* 를 추가할 것.

> 다음 사람에게: **완주 가능성과 첫인상은 다른 작업이다.** 로드맵 전체가 전자를 향해
> 정렬되어 있으므로, 후자를 잊기 쉽다.

---

마감이 이번 주에 하나 남아 있다 (문서 정합성 감사에서 발견 — story-019가 심사 계정
초대와 제출물을 수락 기준으로 걸고 있었다).

**결정: 제출용 단계를 따로 두지 않는다.** 계속 구현하다가 마감 시점의 빌드를 그대로
제출한다. 제출본을 위해 미리 다듬거나 기능을 얼리지 않는다.

### 그래서 지켜야 하는 규칙 하나

> **`main`은 항상 배포 가능한 상태여야 한다.**

제출 전용 안정화 기간이 없다는 것은, **아무 날에나 마감이 와도 내보낼 것이 있어야
한다**는 뜻이다. 이것이 이 결정이 요구하는 유일한 대가다.

실무적으로:
- 각 단계 끝에서 `npm run check` 통과 + **배포본이 처음부터 끝까지 완주 가능**
- 화면을 헐어야 하는 작업(P1의 창구 재작성)은 **한 번에 끝내고 그 안에서 커밋을
  쪼갠다.** 반쯤 헐린 창구로 며칠을 보내지 않는다
- 마감 며칠 전에 큰 리팩터링을 시작하지 않는다

### story-017 / 018 / 019는 미완이다

3일 판이 실제로는 닫히지 않았다 — `production/qa/smoke-2026-08-09.md`가 스스로
*"story-019의 최종 사인오프가 아니다"*라고 적어 두었고
`balance-notes-2026-08-10.md`는 존재하지 않는다. 이 셋은 **낡은 것이 아니라 미완**
이며, 새 계획에서는 **P8(폴리시)에 흡수된다.**

단 `production/qa/` 스모크 절차와 배포 파이프라인(story-019의 검증된 부분)은
**마감 전 언제든 다시 돌릴 수 있어야 한다.** 그것이 위 규칙의 실행 수단이다.

### ⚠ 착수 1순위는 길드마스터북이다 *(2026-08-10)*

> **story-P1-006이 P1의 유일한 Hard 병목이다.**

책은 **일깨우기 재료의 P1 유일 공급원**이다 (소문은 P4). 책이 없으면 **무지 칸을
하나도 못 뚫는다** — 그리고 신설된 `특징 및 약점` 칸은 대비 `C`에 가장 크게 기여하므로,
그 칸을 여는 재료가 책에 없으면 **구조적으로 안 열리는 칸**이 된다.

책은 **공개 등급 기준표의 게재처**이기도 하다 (`commission-form.md` F1 — 책의 첫 장).
그것이 없으면 플레이어는 `D/C/B/A/S`가 무슨 뜻인지 모른 채 등급을 적는다.

**GDD Q2(책 항목 수 8~12)는 이 데이터를 쓰면서 답한다.**

### ⚠ P1에서 반드시 같이 정해야 하는 것 — 지속성(세이브/로드)

**컨셉·로드맵 어디에도 저장이 없었다** (2026-08-09 감사에서 발견). 그런데
캠페인이 8~15시간이고 세션이 30~60분이면 **지속성은 선택이 아니라 필수다.**
한 탭에서 끊지 않고 8시간을 하는 사람은 없다.

그리고 단순 누락이 아니라 **기둥 5와 정면 충돌한다** — *"세이브 스캐밍 없음"*인데
저장이 존재하면 localStorage를 복사해 두는 것만으로 스캐밍이 가능하고, 정적
호스팅이라 서버 검증도 못 한다.

**왜 P1인가**: 저장 포맷은 모든 스키마 변경에 물린다. `Contract` 타입을
재설계하는 지금 같이 잡는 것이 압도적으로 싸다. P3 이후에 붙이면 그때까지의 모든
스키마를 소급 마이그레이션해야 한다.

> **2026-08-10 — 해소됨. `docs/architecture/adr-002-persistence-format.md`가 소유한다.**
> (quick-spec이 아니라 ADR로 썼다 — 지속성 포맷은 위 「ADR을 언제 쓰는가」 기준에 걸린다.)

| 정해야 했던 것 | 결정 |
| ---- | ---- |
| 슬롯 수 · 저장 시점 · 스키마 버전 | **단일 슬롯 자동 저장 · 하루 마감뿐 · `schemaVersion` 필드 + 키에도 버전** |
| **재현 키가 무엇인가** | ~~**매칭된 질문 id.** 타이핑 원문도 클릭 앵커도 아니다~~ → **정정 (2026-08-10). `(칸, 행동, 재료?)` 시퀀스이며 소유자는 ADR-004다.** 질문이라는 개체 자체가 없어졌다 — 칸을 짚는 것이 곧 질문이다 (GDD R4·R10) |
| 세이브 스캐밍 억제 | **막지 않는다. 무의미하게 만든다** — RNG 상태를 함께 저장하므로 되감아 같은 결정을 하면 결과가 바이트 단위로 같다. 파견·의뢰 생성을 다시 굴리는 것이 **불가능**해진다 |

> ⚠ **조사 중 발견한 것 — 세이브가 원리적으로 불가능한 상태였다.** `Rng`가 내부 상태를
> 읽거나 되돌릴 방법을 노출하지 않는다(`state`가 클로저 변수, `createRng(seed)`뿐).
> 컨셉 문서는 *"시드와 결정 로그를 함께 저장한다"* 고 적었으나 **N번 뽑은 뒤의 상태는
> 시드가 아니다** — 시드만 저장하면 복원 시 세계가 처음으로 되감긴다.
> ADR-002가 `snapshot()` 한 줄을 추가해 해결한다. 복원은 `createRng(snapshot)`이며
> **새 팩토리가 필요 없다** (mulberry32의 상태가 32비트 정수 하나이기 때문).

**그러면 2026-08-09의 걱정 — *"질문이 공짜면 전부 물어보기가 지배 전략"* — 은 어떻게

소비가 아니라 **장애물의 정체 확인(진단)** 이기 때문이다 — 진단이 유료면 진단만 하다

**"확인된 장애물 중 어디에 내 지식을 걸까"** 로 옮겨갔고, **거기에는 비용이 걸려 있다**
(헛발 −1).

## P4 — 사람: 가치관 · 관계 · 상실

**왜 이 순서인가**: 게이트를 통과하면 이제 **누구를 보낼지**가 무거워져야 한다.
그리고 P5(세력 평판)가 모험가의 반응을 입력으로 쓰므로 그 전에 온다.

### 들어가는 것

1. **모험가 가치관** — 거절 조건, 공포 대상, 선호 의뢰, 과거 악연
   (에린 예시: 어린이 의뢰는 거절 안 함 / 언데드 공포 / 귀족 혐오)
2. **배정 거부와 그 결과** — 강제 배정 시 충성도 하락, 임무 중 이탈, 길드 탈퇴
   - **⚠ 2026-08-09 — 이 항목의 절반이 선지급됐다.** 배정 거부가 게임을 멈춰서
     P0에서 「거부 → 꺼림 + 강행 시 신뢰 하락」까지 먼저 넣었다
     (`design/quick-specs/assignment-reluctance-2026-08-09.md`).
     남은 것은 **임무 중 이탈**과 **길드 탈퇴**다
   - **길드 탈퇴가 이 단계에서 가장 중요한 이유**: 강행의 대가가 신뢰 하락뿐이면
     `trust`가 0인 순간 **대가가 사라진다** — 가장 강행하고 싶은 상태에서 강행이
     공짜다. 신뢰가 아니라 **사람이 떠나는 것**만이 바닥에서도 작동한다.
     이것을 넣기 전까지 착취 억제 회로에는 구멍이 하나 있다
3. **정보 채널 재배치** — 소문의 출처를 길드원 → 외부인·정보상으로 이동
   (`rumor.ts` 개정). 길드원은 의견·관계·자원만 말한다
4. **길드원 조언** — 사실이 아닌 의견. 배정 전에 거부·자원 여부를 미리 알 수 있다
5. **대화가 신뢰를 올린다** — 길드 홀 순회가 관계 관리가 된다
6. **상실 반응** — 함께 나갔던 동료에게 `lostComrade` 기억. 며칠간 조언·자원 안 함
   (자료 구조와 대사 4종이 이미 있다: `types.ts`, `text.json`)
7. **영입 하이브리드** — 돈 주고 데려오기(고를 수 있음) + 명성으로 지원자 찾아오기
   (무작위, 무료). 가입비는 받지 않는다

### 완료 기준

- 특정 모험가를 배정하려다 거부당하는 경험이 발생한다
- 동료가 죽은 뒤 남은 사람의 태도가 달라진 것이 눈에 보인다
- 명성이 오르면 지원자가 실제로 찾아온다

## P5 — 세력 평판

**왜 이 순서인가**: 도덕 축이 기계적으로 성립하는 곳. P4의 모험가 반응이 있어야
"시민 편을 들면 귀족이 등을 돌리고 일부 모험가는 좋아한다"가 완성된다.

### 들어가는 것

1. **세력 6종** — 시민 / 귀족 / 상인 / 범죄조직 / 모험가 / 왕실
2. **의뢰 종류의 도덕값** — 별도 게이지가 아니라 **어느 세력이 좋아하고 싫어하는가**
3. **평판의 결과** — 세력별 의뢰 유입량, 가격, 특수 사건(세무 조사, 감찰관 방문)
4. **명성 단일 수치 폐기** — 기존 `reputation`을 세력 평판으로 승격. 난이도
   스케일링 입력도 함께 바뀐다
5. **의뢰인 직업 확장** — 성직 / 군인 추가

### 완료 기준

- 시민 평판을 올리면 귀족 의뢰가 실제로 줄어든다
- 플레이어가 "어느 편에 설 것인가"를 의식적으로 선택한다
- **게임이 어느 쪽도 옳다고 말하지 않는다**

## P6 — 세계 변화

**왜 이 순서인가**: **가장 비싸다.** 그리고 P5의 세력이 있어야 후과가 "누구에게
좋고 누구에게 나쁜지"로 표현된다. 기둥 7이 여기서 성립한다.

### 들어가는 것

1. **후과 규칙 테이블** — 의뢰 결과 → 지역/세력/경제/치안 변동
   **깊이 1로 제한한다.** 후과의 후과는 새 의뢰가 되어 다시 깊이 1부터
2. **후과가 새 의뢰를 만든다** — 산적 증가 → 호위 의뢰 유입
3. **인과의 가시화** — 후과가 나타날 때 **원인이 된 의뢰를 명시적으로 참조**한다.
   술집 소문이 연결을 말해준다 (*"그 고블린들이 있을 때는…"*)
4. **길드 장부 / 과거 기록 조회** — 플레이어가 인과를 직접 추적할 수 있어야 한다

### 완료 기준

- 플레이어가 **스스로** "아, 저번 그 의뢰 때문이구나"를 알아차린다
- 후과가 처벌이 아니라 **다른 곳으로 옮겨간 문제**로 읽힌다
- 깨끗하게 끝나는 의뢰가 하나도 없다

### 리스크

**가장 위험한 단계다.** 인과가 안 보이면 후과는 그냥 재수 없는 사건이 되고,
컨셉 문서의 *"창발이 무작위처럼 느껴질 위험"*이 현실화된다. 3번(가시화)을
1~2번보다 먼저 설계할 것.

### 먼저 쓸 문서

- `design/quick-specs/world-consequences-*.md` — 후과 테이블, 깊이 제한, 가시화 규칙

| 3. "LLM이 API를 지어내지 않는다" | **생존하며 더 무거워졌다** |

3번이 왜 더 무거워졌는가: 3일 프로젝트에서 환각 비용은 사흘치였다. 이제는 P0~P8을
거치는 장기 개발이고 **에이전트 주도 개발이 기본 작업 방식**이므로 환각 비용이 전
기간에 누적된다.

**재검토 시점: GATE 통과 후.** P1~P3은 설계 불확실성이 가장 높은 구간이고, 그
구간에서 툴체인 디버깅에 주의를 빼앗기는 것이 가장 비싸다.

**이 결정이 옳았는지 아는 법**: GATE까지 툴체인 관련 막힘이 0건이면 옳았다.
*"이 API가 이 버전에 있나"* 확인에 세션당 여러 번 걸린다면 근거 3이 이미 죽은
것이고 상향해야 한다.
