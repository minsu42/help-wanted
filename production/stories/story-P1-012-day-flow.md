# Story P1-012: 하루 진행 — 의뢰인 세 명이 차례로 앉는다

> **Phase**: P1 | **Status**: Ready | **Layer**: Integration | **Type**: Logic/UI
> **GDD**: `design/gdd/intake-system.md` (v6.2) R7 · U1~U5 · Dependencies / P1 완료 기준
> **ADR**: ADR-002 D5·D6·D9 / ADR-003 D5
> **Created**: 2026-08-10

## Context

P1의 청취·의뢰서가 각각 완성되어도 **하루의 주인이 없으면 게임은 이어지지 않는다.**
현재 3일판의 `main.ts`는 창구·홀·배정 화면 각각에서 하루를 넘길 수 있고, 새 P1 설계가
요구하는 *"의뢰인 3명이 정해진 순서로 와서 의뢰서를 남긴다"* 는 흐름이 없다.

이 스토리는 새 규칙을 만들지 않는다. 이미 확정된 마디를 하나의 진행 상태로 묶는다.

```
하루 시작
  → 의뢰인 1 청취 → 등급 기입(선택) → 도장
  → 의뢰인 2 청취 → 등급 기입(선택) → 도장
  → 의뢰인 3 청취 → 등급 기입(선택) → 도장
  → 하루 마감 → advanceDay 1회 → 자동 저장 1회 → 다음 날
```

**하루 행동 칸도, 의뢰인 선택도, 질문 횟수 제한도 없다.** 하루를 조이는 자원은 각
의뢰인의 인내뿐이고, 그것도 일깨우기·들이대기의 헛발에만 줄어든다.

## Acceptance Criteria

### A. 세 명, 고정 순서

- [ ] 하루 시작 시 의뢰인이 **정확히 3명** 준비되고, 같은 시드와 같은 상태에서는
      같은 세 명이 같은 순서로 온다
- [ ] 플레이어가 의뢰인을 고르는 목록·대기열 재정렬·새로고침 버튼이 없다
- [ ] 앞 의뢰인의 의뢰서가 도장되기 전에는 다음 의뢰인으로 넘어가지 않는다
- [ ] 세 의뢰인의 `IntakeState`·대화 이력·인내가 서로 섞이지 않는다
- [ ] 세 번째 도장이 찍히기 전에는 `advanceDay()`가 호출되지 않는다

### B. 막다른 길 없음

- [ ] **아무것도 묻지 않고**, 등급도 고르지 않은 채 도장해도 다음 의뢰인으로 진행한다
- [ ] 인내가 0이 되어 의뢰인이 퇴장해도 의뢰서의 등급 선택과 도장은 남아 있다
- [ ] 게이트웨이가 처음부터 끝까지 차단되어도 세 명의 의뢰서를 모두 도장할 수 있다
- [ ] 등급 미기재 의뢰서는 빈 등급을 보존한다. P2 지원 판정이 이를 `S`로 간주하는
      규칙을 P1 화면이 미리 적용하지 않는다
- [ ] 한 의뢰인의 실패·퇴장이 다음 의뢰인의 초기 인내나 칸 상태를 바꾸지 않는다

### C. 하루 마감과 저장 경계

- [ ] 세 번째 도장 직후 **`advanceDay()`가 정확히 1회** 호출된다
- [ ] ADR-002 D5의 자동 저장은 `advanceDay()`가 끝난 뒤 **정확히 1회** 호출된다
- [ ] 첫째·둘째 의뢰인 도장, 질문, 수첩 열기, 등급 재선택에는 저장 호출이 없다
- [ ] 저장 실패는 다음 날 진행을 막지 않고 사용자에게 한 번만 알린다
- [ ] 하루 중간 새로고침은 그날을 복원하지 않는다. 마지막 하루 마감 저장으로 돌아가는
      것이 명시된 동작이며, 부분 복원을 시도하지 않는다

### D. 결정론과 LLM 경계

- [ ] 같은 시드 + 같은 `(칸, 행동, 재료?)` 시퀀스면 세 의뢰서와 다음 날 상태가 같다
- [ ] 게이트웨이 목 응답을 완전히 다른 문장 집합으로 바꿔도 세 의뢰서와 저장 바이트가
      동일하다. 달라지는 것은 화면 대사뿐이다
- [ ] 계약이 바뀔 때 LLM 대화 이력이 초기화되고 이전 의뢰인의 문장이 다음 요청에
      들어가지 않는다

### E. 접근성과 화면 연결

- [ ] 키보드만으로 세 의뢰인을 연속 처리하고 하루를 마칠 수 있다
- [ ] 현재 순서를 `1/3` 같은 완료 점수로 표시하지 않는다. 의뢰인이 바뀌는 장면과
      종이 교체로 진행을 알린다
- [ ] 화면 교체 때 이전 화면의 루트 리스너가 제거된다. 클릭 한 번이 두 계약에
      전달되지 않는다
- [ ] 클릭 후 규칙 상태 반영은 100ms 이내다. LLM 대사만 2초/8초 예산의 예외다

## Implementation Notes

- 하루 흐름의 소유자는 조립 지점(`src/main.ts` 또는 그로부터 추출한
  `src/application/dayFlow.ts`) 하나다. 화면 모듈이 직접 `advanceDay()`를 호출하지 않는다
- 진행 상태는 최소한 `currentClientIndex`와 그날의 3계약을 가진다. **화면 DOM을 상태로
  쓰지 않는다**
- 도장은 계약 하나의 커밋 지점이지 저장 지점이 아니다. 저장 지점은 세 번째 도장 뒤
  하루 마감 하나뿐이다
- 기존 홀·배정 화면의 `onAdvanceDay` 경로는 P1 세로 슬라이스와 충돌한다. 이 스토리에서
  조용히 삭제하지 말고 P2/P4 전까지 어느 경로가 레거시인지 주석과 테스트로 고정한다
- 대화 이력과 인내는 계약 단위 휘발이다. `SaveFileV1`에 넣지 않는다 (ADR-002 D9)
